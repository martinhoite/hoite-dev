# Design System

The Hoite Dev design system is the shared foundation for consistent UI across Hoite Dev projects. It brings together design tokens, themes, shared styling contracts, React component implementations, Vue component implementations, and package-level documentation so the same visual rules can be applied consistently across apps and docs.

Shared contracts document the design-system rules owned by `@hoite-dev/ui`. Package pages document how each workspace package owns, exposes, or consumes that contract.

## System layers

The Hoite Dev design system can be read as a simple flow:

1. Design tokens: raw values for color, spacing, typography, size, radius, motion, and related foundations.
2. Shared styling contracts: framework-independent class contracts, semantic defaults, docs metadata, and visual rules built on those tokens.
3. Framework implementations: React and Vue components that consume the shared styling contracts and add framework-specific typing and runtime behavior.
4. Application usage: app-level screens and features that consume the framework packages without moving business logic into the design system itself.

## Package responsibilities

The core package boundaries stay deliberate:

- `@hoite-dev/ui` owns the shared styling foundation, tokens, themes, CSS custom properties, shared CSS, CVA definitions, style-related TypeScript exports, and shared docs metadata where relevant.
- `@hoite-dev/ui-react` owns the React component implementations, React-specific typing, and DOM behavior while consuming styling contracts from `@hoite-dev/ui`.
- `@hoite-dev/ui-vue` owns the Vue component implementations, Vue-specific typing, and DOM behavior while consuming styling contracts from `@hoite-dev/ui`.

Package docs own deeper package-specific details. This overview page only establishes the boundary between them.

## Component groups

The Hoite Dev design system groups primitives by role in the system:

- Static primitives cover display and structure components.
- Action primitives cover interactive components.
- Form primitives cover form controls, labels, helper text, error text, and validation-related primitives.

These groups keep the design-system surface aligned across docs, source structure, and framework Storybooks.

## Themes and tokens

The Hoite Dev design system uses CSS custom properties for tokens and themes. Foundational tokens stay stable across themes, while theme-aware tokens such as semantic color values can resolve differently by theme. The [Tokens](/design-system/tokens/) page documents those values in detail.

## How To Navigate

Start with this overview when you need orientation. Move into [Tokens](/design-system/tokens/) when you need the raw values and theme behavior, into [Shared Contracts](/design-system/contracts/) when you need the `@hoite-dev/ui` component contract, and into [Packages](/packages/) when you need package-specific exports, ownership, or implementation detail.

## What Stays Outside

The Hoite Dev design system does not own:

- application-specific business logic
- routing behavior
- CMS data shaping
- app-level layout decisions
- project-specific feature behavior
